# Changelog

All notable changes to MaiSim are listed here, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).
Each pull request adds its line under **Unreleased**; a release moves them under a version number.

## [Unreleased]

### Changed
- **The screen in columns: Circuit, Scope, Control and AI, side by side.** Four buttons in the header turn each column on and off; the columns that are on share the width, with nothing on top of anything.
  - Scope and Control are separate columns now (they were tabs of one dock), so the end of a run opens the Scope next to the code instead of hiding it. The "Scope beside / below" buttons are gone.
  - The AI is the fourth column (it used to open over the Scope and the Control) and the fourth button, which carries the proposal dot and the "working" pulse of the old floating button. **⇔** switches it between narrow (440 px) and half the window.
  - Any combination works, even without the circuit; the last column cannot be turned off.
  - Each column has its own divider. Each column has a minimum that still works (Control 560 px, Scope and AI 360 px). When space is short, the circuit gives way first, and the column just opened or dragged keeps the width asked for, as far as the others still fit.
  - Dragging the AI border over the Scope no longer gets lost (the Scope's frame swallowed the mouse).
- **The Ts info says what Ts is:** sampling and computation of the control (every Ts the measurements are read and `passo()` runs, like the ADC interrupt in a DSP), in three short lines.

### Fixed
- **The launcher's watchdog (#241) could kill a running engine during a long run.** The engine serves one connection at a time and the simulator keeps its own open, so each 5 s port check waited in the engine's queue; after ~50 s the queue was full, the port looked closed and the engine was restarted in the middle of the run. The watchdog now watches the processes the launcher started by the process itself, and checks the port only for one it has no process for. The `religa_gecko_api` test now stays idle 70 s with the editor connected and checks nothing is restarted.
- **When Gecko or the editor engine fell, MaiSim did not bring them back**, and the app stayed on "no editor engine" until it was closed. On the phone, after Android killed only one of the two Java processes, it got worse: every new start gave up on the "half up" Gecko and asked for `--parar`, which nobody can run there, so the only way out was to uninstall.
  - Every 5 s, the launcher now checks Gecko and the engine and restarts whichever fell. A new engine takes seconds. A new Gecko takes up to a minute, and it reopens the circuit the editor had, with a copy of anything unsaved, as before.
  - While it restarts, the error says the engine is being restarted, not "no editor engine".
  - It restarts at most 3 times in 10 min and then stops and says so in its log, so a Gecko that keeps crashing does not loop forever.
  - At start, a Gecko running without its engine is adopted and only the engine starts. An engine left without its Gecko is stopped, but only MaiSim's own engine on that port, never another program, and everything starts again.
  - New test `religa_gecko_api` kills each process the way Android does, on a throwaway launcher (ports 7480–7486).

### Changed
- **Every run ends about 0.25 s sooner**, a ~30% gain on the examples without Python control (boost 0.84 → 0.58 s; inverters and H-bridge alike). When a simulation ended, GeckoCIRCUITS always waited 300 ms so as not to race the refresh of its own scope windows, which MaiSim never opens. Patch `0014` waits only when a Gecko scope window is on screen. The results are unchanged, bit for bit (A/B on 7 examples).

### Added
- **Export the C control to STM32, Simulink / OPAL-RT, Typhoon HIL, PLECS and FPGA (Vitis HLS)**, besides the TI C2000, all from the same C that runs in the simulation. The dialog lists the six targets.
  - **STM32:** the HAL ADC callback skeleton.
  - **Simulink / OPAL-RT (RT-LAB) / Simulink Real-Time:** a level-2 C S-function (`mex`), with the measurement and actuation order.
  - **Typhoon HIL:** the three sections to paste into the C function block, with the control and its modules as one text and the ports named `m_…`/`u_…`.
  - **PLECS:** the three sections for the C-Script block.
  - **FPGA:** the `maisim_top` top function for Vitis HLS (HLS generates the VHDL/Verilog from this C) and a testbench that reads the same CSV as `replay.c`.
  - Each package has a `LEIA.md` section for its tool (pt/en).
  - The target skeletons compute time as n·Ts. Adding Ts every sample accumulates rounding error and shifts the PWM edges.
  - A test runs each target's code on the PC (S-function, Typhoon and PLECS blocks, HLS testbench) on the same measurements, and it matches the C in the simulation bit for bit. The STM32 skeleton compiles.

### Added
- **The packages bring their own C compiler (TinyCC)**, so the C control runs where there is no compiler: the Windows installer, the AppImage (x86_64 and ARM) and the Android app.
  - On Linux the TinyCC 0.9.27 is built from its source (`pacote/tcc.sh`, SHA-256 pinned, without the memory checker that no longer builds with today's glibc). On Windows it is the official win64 build. The license (LGPL v2.1) goes in `maisim/tcc/COPYING`, and the credits name it.
  - On Linux the embedded TinyCC compiles with MaiSim's own minimal C headers (`simu/controle_c/libc`) instead of the system's, and links without the system C library (the functions come from the Python process). It compiles the same on any machine, even without developer tools.
  - With it, the C gives exactly the same results as with gcc, bit for bit, in the buck and with the whole control library (the PLL with sin and cos). A `printf` in the C now reaches the control log as it happens.
  - The package smoke test runs a C control, and the CI builds the TinyCC to test it.
- **Export the C control to the hardware (TI C2000)**. On the C view, **⤓ Export** builds a `.zip` from the same C that runs in the simulation, with one folder per controller (one firmware each). Each folder has:
  - the code and its modules, unchanged;
  - `maisim_controle.h` in the chosen precision (`float` for the C28x FPU, recommended, or `double`);
  - `maisim_sinais.h` with its indices, and `maisim_parametros.h` with Ts and the panel's parameter values;
  - `maisim_alvo.c` (scope and messages, to fill in with your communication);
  - `alvos/c2000/c2000_isr.c`, the ADC interrupt skeleton (read `m[]`, call `maisim_passo`, write `u[]`), with a TODO for each measurement's channel and each actuation;
  - `teste/replay.c`, the same control on the PC from a CSV of measurements;
  - a `LEIA.md` with the steps in Code Composer Studio and the caveats (float, TMU, ePWM, timing).
  - A test checks that the package compiles and that `replay.c` gives exactly the same actuations as the C in the simulation, bit for bit. Other targets (STM32, Typhoon HIL, OPAL-RT/Simulink, PLECS, FPGA via HLS) show as *coming soon*.

### Changed
- **The language selector is Python | C**: FPGA is not a language but a target (its C goes through HLS), so it moves to the Export targets.

### Changed
- **MaiSim's AI stands apart, in a drawer opened by a floating button.** On the desktop, the conversation used to open as a third column inside the Control panel and squeezed the code to half its width.
  - Now a round button in the bottom-right corner opens a drawer on the right, full height below the header, over whatever is on screen (circuit, control or scope).
  - Dragging its left edge changes the width (double click: the default). The dock is back to Scope | Control, and opening or closing the AI does not change it.
  - The button pulses while the AI is answering and shows a dot when a proposal arrived with the drawer closed.
  - On the desktop, the floating button is the only way in (the Control bar's **AI** button is gone; on the phone it stays and leads to the AI view). "Ask the AI" on an error and the ✦ window open the same drawer.
  - The automatic **Code ⇄** request runs behind; if it fails, the Control panel says so, with a button to open the conversation.
  - On the phone, the AI view is the drawer, full screen. The old divider and "beside / below the code" button are gone.

### Added
- **Several controllers in C, talking over the network**. With the controllers list (acquisition, control, one per subcircuit…), the C view runs the same controllers, each in the `.c` named after its `.py` (`aquisicao.py` → `aquisicao.c`).
  - Each controller compiles in its own folder, with a `maisim_sinais.h` holding only its own measurements and actuations.
  - The modules (the `.h`/`.c` files that belong to no controller) go into each controller that includes them, so a `leitura.c` can be reused by several DSPs, each running its own copy.
  - Messages are `maisim_envia("controle", "i", v)` and `maisim_recebeu("aquisicao", "i", &v)`, Python's `envia`/`recebe` with the same network latency.
  - In the panel, each controller shows under its `.c` with its card. One without its `.c` yet shows as *missing: create*, and a click creates it from the template.
  - The Diagram on the C view shows the `.c` files and reads the messages from `maisim_envia`.
  - MaiSim's AI compiles each controller of its proposal with that controller's indices, and is told how to write several controllers in C.
  - The acquisition + control example runs bit-identical in C and in Python, with latency 0 and 2.5·Ts.

### Added
- **Control library: ready-made modules in Python and in C** (`simu/biblioteca_controle`): **PI** (saturation and anti-windup), **PWM** (sawtooth or triangular carrier), **first-order low-pass filter**, **ramp** (rate limiter for a soft start) and **three-phase SRF-PLL** (uses the PI). In the Control panel, **+ File** now offers *Empty* or one of them: on the Python view it creates `pi.py`; on the C view, the pair `pi.h`/`pi.c`, with the modules it uses (the PLL brings the PI). Each module does the same operations in the same order in both languages, so **Compare Python × C** gives bit-identical results; the usage is in the comment at the top of each file, in pt or en. A test runs every module in Python and in C on the same inputs and checks every output bit for bit, and the buck example controlled with the library's PI and PWM runs bit-identical in Python and in C. MaiSim's AI is told to use them instead of rewriting.

### Fixed
- **C code calling `sin()` and `cos()` of the same angle could differ from Python in the last bit**: gcc merges the two calls into `sincos()`, which sometimes rounds differently. The C control is now compiled with `-fno-builtin-sin -fno-builtin-cos` (as `-ffp-contract=off` already avoids fused multiply-adds), so the same operations give the same double as Python.

### Added
- **C modules in the Control panel**, as C firmware is organized: on the C view, **+ File** creates the pair `name.h` (what the module offers: the declarations, with an include guard) and `name.c` (the code); `controle.c` does `#include "name.h"` and calls its functions in the same sample. The file tree follows the `#include`s (`controle.c` → `pwm.c` → `pwm.h`), like the Python tree follows the imports, and the **Files** count on each view counts only that language's files (the C view showed the Python count). The modules compile together with `controle.c` (a run with the PWM in `pwm.c` matches the single-file one bit for bit), a compile error points at the module's file and line, and MaiSim's AI may write `.c`/`.h` files: converting a `controle.py` with modules gives one `.h`/`.c` pair per module. For now C runs as a single controller (several C controllers, sharing modules between DSPs, come later).

### Fixed
- **With the Control panel on C, asking the AI for a control gave Python**: the AI did not know which language the panel runs. Its `CONTEXTO.md` now says “Control language: C” or “Python” (the Python | C selector), and the rules say a control request goes in that language unless you ask for the other; on C, the AI writes `controle.c` (from scratch, if there is only the template) and leaves `controle.py` as it was.

### Fixed
- **The C code had no colors in the Control panel** (black text, like a notepad, while the Python was highlighted): the local Monaco (`simu/vendor.sh`, so the editor works offline) only kept the Python language. It now keeps C too (Monaco's `cpp`), and runs again when a language is missing; the developer version's **Update** also runs it when the local Monaco is there, so existing clones get the C colors.

### Added
- **The AI converts the control between Python and C ("Code ⇄")**: in the Control panel, **⇄ Generate C from Python** (on the C view) or **⇄ Generate Python from C** (on the Python view) asks MaiSim's AI for the same control in the other language, with the same operations in the same order; you see the diff and apply it, as with any proposal (per file, and "back to before" brings the C back too). The AI's folder now has `controle.c` (the template if there is none), `maisim_sinais.h` generated from the panel and `maisim_controle.h`, and the AI may write `controle.c`; the proposed C is compiled to check it (not run), so an error shows on its line before you apply, and the proposal's test runs the C. A badge says **in sync ✓** while both files are the ones from the last comparison that matched (and **out of sync** once either changes). With **Code ⇄** on, saving a change in one of them asks the AI for the other after a few seconds, applies it and compares both.

### Added
- **The control in C, running inside the simulation (software-in-the-loop)**: a `controle.c` can run in place of the `controle.py`, compiled and called every Ts through the same path (delays, events and Gecko's per-sample stepping unchanged). In the Control panel, a **Python | C** selector (FPGA greyed out, coming later) chooses the language that runs and the one the panel shows: the files, the tabs (the C one with C highlighting, created from a template) and the controller block in the diagram; the tables' "In the code" column finds the uses in both (`m[M_i_L]`, `p[P_Kp]`, `u[U_g] =`). **Compare Python × C** runs the circuit with each and shows, signal by signal, whether they match bit for bit or the largest difference; both runs stay in the Scope to compare A/B. MaiSim generates `maisim_sinais.h` from the panel (the indices `M_<measurement>`, `P_<parameter>` with `P_Ts`, `U_<actuation>`); the contract is `simu/controle_c/maisim_controle.h` (`maisim_tamanho_estado`, `maisim_iniciar`, `maisim_passo`, `maisim_scope`): state in a struct, no `malloc`, ready for a DSP. A compile error comes back with the file and line, like a Python error. With the same operations in the same order, the C run matches the Python run bit for bit (the PWM buck example); `float` precision (as on a C28x) shows its effect. For now: one controller, needs `tcc`, `gcc` or `cc`, and the C is written by hand; the AI converting between Python and C and the compiler bundled in the packages come next.

## [0.3.9] - 2026-11-04

### Added
- **Control blocks rotate** (R, the panel's Rotate, or Space while holding the block): MaiSim's Gecko now rotates them (patch `0012`: the original GeckoCIRCUITS keeps every control block pointing down, `RegelBlock.rotiereSymbol()` is empty). The terminals follow the orientation in Gecko, so a wire to a rotated block connects in the simulation; the editor draws the block standing or reversed (box and legs turned, the texts upright, the value and the GATE/TF line beside a standing block). Blocks whose terminal positions MaiSim only guesses, and text boxes, still do not rotate (a message says why); subcircuits still do not rotate either. Wires are not re-routed when you rotate (as with the power components): connect them again at the new terminals. **Compatibility:** a circuit with a rotated control block opens in the original GeckoCIRCUITS with the block pointing down and its wires loose; inside MaiSim it opens as saved.
- **Editor (PC): mouse and keyboard shortcuts**: pressing the mouse wheel and dragging moves the view, in any mode (no browser autoscroll or paste); holding a part (the button pressed on it), **Space** rotates it, **X** sets it horizontal (already horizontal, it mirrors it) and **Y** sets it vertical (already vertical, it mirrors it); releasing puts it where the mouse is. Gecko cannot mirror (only four rotations): mirroring is a 180° turn (the terminals swap, a diode reverses), in one Undo step, and horizontal, vertical and mirror work on parts with their terminals in a line (R, L, C, diodes, switches, GAIN, CONST, GATE…); otherwise a message explains. The wheel already zoomed. The component panel's hint lists the shortcuts.
- **Shortcuts in the desktop rail**: a keyboard button opens the list of every mouse and keyboard shortcut (editor, wires, simulation and file, scope), in pt and en.
- **Phone app: “Open now” at the top of Home**: the circuit open on the server (MaiSim keeps it, even with the app closed), with “not saved” when it has changes; one tap opens it as it is, changes kept, to save or undo (a new circuit not saved yet shows as “new circuit (no name)”). Before, the phone showed no open circuit (its Circuit tab was greyed out), so when Update refused because of unsaved changes there was no way to find them without the PC screen. A refused Update also refreshes this card.
- **Phone app: + New circuit in Home**: a blank sheet, as on the PC. With something unsaved on the server, the app asks first (open it to save, or discard the changes and create), then the editor asks only for the name, and the app's title is that name. The phone could only open existing circuits.
- **Phone app: ⋯ → Close the circuit**: the PC's Close, with the same question when something is unsaved (save, save as or discard); then the app goes back to Home with the circuit's tabs greyed out. The phone had no way to close a circuit.
- **Phone app: Open in a subcircuit's panel**: on the PC you enter a subcircuit by double-clicking it, which a phone never delivers (the first tap opens the panel and moves the view).
- **Phone app: the editor's errors show up**: they went to the editor's header, which the phone hides (a run that failed, a wire that could not be made, a save that failed); they now appear in the app's notice, in red, and a Save from the ⋯ menu says where it saved.
- **Phone app: Compare A/B one tap away**: the scope's collapsed header on the phone has a **Compare A/B** button that opens the choice of runs A and B and enters Compare (it was there, but only behind the unlabelled ▾). On the phone the collapsed header now wraps instead of running off the screen, so ▾ and Compare A/B stay visible on narrow phones.
- **Phone app: “Test versions” switch in Home → Settings**, next to Update: the same update channel as the PC's update window (on: the -rc releases too; off: only the stable ones). The phone had no way to change it.

### Fixed
- **Editor: R on the thermal reference (TREF) or the loss source (Pv)** sent a rotation Gecko ignores; it now says Gecko does not rotate them, like control blocks.
- **Phone app: a new circuit no longer says “opening…” forever**: with no parts, the top line now says “editing · blank sheet” (0 parts read as “not open yet”), and the “editing · N elements” count follows the parts you place or delete (it kept the count from when the circuit opened, even the previous circuit's).
- **Phone app: the ⋯ menu of a new circuit showed “__novo__”** (an internal name) as its title; it shows the circuit's name.
- **Phone app: the AI buttons in Control** (IA, and “ask the AI” on a test error) opened the conversation in a column the Control view hides; they now switch to the AI tab.
- **Phone scope: no ☰ Index button** (the index does not show on the phone, so the button did nothing), and a layout saved with “one section at a time” shows all sections on the phone (there was no index to switch sections).
- **Phone app: the Scope tab shows the open circuit's runs**: opening a circuit showed the server's last run, from whatever circuit ran last, and the previous circuit's scope stayed after opening another one. It now shows the last run of the circuit you opened; with none yet, a short notice (tap ▶ to simulate) instead of a scope, which would follow another circuit's live run.

### Removed
- **Phone app: the “Desktop version” link in Home → Settings**: it opened the PC screen inside the app with no way back to the phone screens (its one phone use, the update channel, is now the “Test versions” switch). The phone app is the MaiSim of the phone; the PC screen stays on the PC.

## [0.3.8] - 2026-11-03

### Added
- **The Android app checks the phone before setting up**: not enough free space for what is still missing (the Linux base, MaiSim) stops with a clear message (how much it needs, how much is free) instead of failing halfway; less than 3 GB of RAM shows a warning and lets you try. Android 10+ and 64-bit ARM are enforced by Android's installer itself.

The app carries proot (Termux's, prebuilt and checked by SHA-256) as native libraries, and on first launch downloads and sets up Ubuntu Base 24.04 (arm64, checked against Canonical's SHA256SUMS), the basic tools (curl, for the AI installers) and this version's MaiSim ARM package, with a progress screen. Your circuits stay outside Ubuntu, and MaiSim's Update button replaces only the program (tested on a real phone from rc3 to rc4). The packages workflow builds it, signs it with the official key and checks the certificate against the one registered with Google (`pacote/android/apk/chave.sha256`) before attaching `MaiSim-Android-<version>.apk` (and `MaiSim-Android.apk`) to the Release. Third parties: `pacote/android/apk/NOTICE.md`.
- **Phone app: Move a part**: tap the part, then **Move** in its panel; the next tap on the sheet is where it goes (Undo brings it back). Dragging a finger always moves the sheet, so parts never move by accident. (The first try, touch and hold to drag, did not work on a real phone: Android takes the long press for itself.)

- **Phone app: version and Update in Home → Settings**, the same Update as the PC's rail (on Android, the ARM folder: download, swap, restart, and the page reloads on the new version).
- **The AI can propose circuit values**: besides the control, MaiSim's AI may now propose new values for parameters of components that already exist (and for `$` variables), e.g. for a rectifier with ΔV ≤ 10 % it explains the calculation and proposes `C.1 · C: 100 µF → 820 µF`. It writes them in `circuito.json` in its working folder (the AI's context now lists each component's panel parameters with value and unit, and the `$` variables); MaiSim checks each item against the open circuit and drops what does not exist, is not a number or comes from a `$` variable, with a warning. The proposal card shows before → after; nothing changes until you click Apply, which applies them as one editor edit (undo reverts it; "back to before" too). Adding, removing, rewiring or renaming components stays with you.
- **MaiSim for Android, the phone app (`/movel.html`)**: a touch app with tabs (Home, Circuit, Scope, Control, AI) over the same MaiSim: the same routes, circuits and runs as the PC. Home lists your circuits and the examples, imports a `.msd` and has the settings (theme, language, AI accounts). Circuit, Control and AI are the editor itself in a phone view (`/maisim/simu/?movel=1`): full screen, two-finger zoom and pan, the part panel and the palette rise from the bottom (with the keyboard), and nothing takes the focus on its own, so the keyboard only opens when you tap a field. The ⋯ menu has the simulation settings, `$` variables, layers, save, undo and Export `.msd`. ▶ shows the progress on top and leads to the Scope tab (the scope itself, `?movel=1`: full-width panels, a compact header, two-finger zoom in time and a finger cursor). Inside a subcircuit, a “‹ main” button goes back (the PC's breadcrumb is in the hidden header). It installs as its own app, “MaiSim Android” (manifest with `start_url` `/movel.html`). New screen test `movel_tela` (20 checks).
- **The Android installer starts MaiSim and opens the phone app**: after installing, it runs `maisim`, which starts MaiSim in the background and, when it answers, opens `http://localhost:7100/movel.html` in the browser (already running: it just opens the app). The Termux:Widget shortcut does the same.
- **MaiSim on Android in one command**: in Termux, `curl -fsSL https://raw.githubusercontent.com/marcelopedroso/maisim/main/pacote/android/instala.sh | bash` installs proot-distro and Ubuntu, downloads MaiSim's newest ARM package (checked by SHA-256) into `~/maisim-app` with what it needs from the system, and creates the `maisim` command (and a Termux:Widget shortcut): type `maisim` and open `http://localhost:7100` in the phone's browser. The installer stops with a clear message when run outside Termux or inside the Ubuntu.
- **The folder version updates itself**: the Update button downloads the new `.tar.gz`, checks it, extracts it next to the current folder (no paths outside it), swaps the whole folder and restarts, like the AppImage. It refuses when your data is inside the program's folder (it would delete your circuits).

## [0.3.7] - 2026-11-01

### Security
- **A website open in the browser can no longer reach MaiSim on this machine.** Everything already listened only on 127.0.0.1, but a page from any site could still send requests to `localhost`: it could drive the Gecko screen through the noVNC WebSocket, make the editor engine run commands (including writing files), delete the scope's recordings with a hidden POST, and read the API from a domain that resolves to 127.0.0.1 (DNS rebinding). The fixes apply to the Windows installer and the AppImage too: they use the same page, servers and engine.
  - **The page (`app/pagina.py`)** accepts only its own Host (`localhost`, `127.0.0.1` or `[::1]` with its port; anything else gets 421). It reads request headers strictly: a bare line break, a folded line, a duplicate Host or Content-Length, Content-Length together with Transfer-Encoding, a target that does not start with `/` or an invalid header name get 400, so no hidden header reaches the modules. Headers must arrive within 15 s. WebSockets are allowed only to the Gecko screen, and only with the page's own Origin (403 otherwise). The page's life signal (`/maisim/vivo`) only counts when it comes from the MaiSim page: a fake signal from a website kept MaiSim running for up to 24 h after its window closed.
  - **The simulator and the scope** check the Host on every request, also when called on their own ports (7101, 7102) without the page. The scope's `/apagar` requires the same check as the simulator (local Host, the page's Origin, `X-MaiSim: 1`); the scope's delete dialog and the home page's trash send the header. `/publicar` takes only JSON from no other origin or site, up to 256 MB, which is what the simulator and `run.py` already send.
  - **The editor engine (port 7104)** drops a connection whose first line is not a MaiSim command: the request line of an HTTP request, or control bytes (the start of TLS, or STUN from a WebRTC TURN connection). A website could POST to `localhost:7104`, and the engine ran the lines of the body as its own commands: `SAVEAS` could write a file anywhere the user can. A connection must also send its first command within 5 s, so a silent one cannot hold the engine's one-at-a-time queue.
  - **The Gecko screen in the browser is off by default.** It is only for debugging Gecko (it left the side menu on 18/10), so the launcher no longer starts x11vnc and websockify unless `.env` has `MAISIM_TELA_GECKO=1`: no extra ports, and no x11vnc scanning the display during runs. With the screen off, `/maisim/gecko/` says how to turn it on. The Windows installer never had it; `gecko/sobe.sh` (the terminal developer mode) still starts it, with the same protections.
  - **When it is on, the Gecko screen is view only and protected.** x11vnc runs with `-viewonly` (and noVNC in view-only mode): Gecko is MaiSim's back end, and no click or key reaches it through the screen. It asks for a random password, new at each start (`vnc.senha` in the cache, created readable only by the user; before, it ran with `-nopw`), and websockify accepts the WebSocket only from the MaiSim page's origin, also directly on its own port. The noVNC page gets the password from `/maisim/gecko-senha`, which answers only the MaiSim page itself (`X-MaiSim: 1`, same origin). Opened directly on its own port (7105), the page does not connect and says to open it through MaiSim. The password and the origin checks keep websites out; like the rest of the local API, they do not separate other user accounts on the same computer.
  - **After an update with Gecko kept running** (an unsaved circuit), the launcher restarts the engine and the Gecko screen with the new rules instead of adopting the old ones; Gecko itself and the circuit stay.
  - **The Vite dev server** (`MAISIM_PAGINA=vite`) checks the same: only a local Host (421 otherwise, also for WebSockets), the Gecko screen's WebSocket only from the page's origin, and `/maisim/gecko-senha` only for the page.
  - New test `seguranca_api` tries each attack and checks that it is refused: the no-cors POST, the WebSocket from another origin, a foreign Host on the page and on the modules' ports, a smuggled header, a header trickled in pieces (the 15 s limit is for the whole header, not per piece), an HTTP request, control bytes and a silent connection to the engine (on an engine of its own, compiled from the current code). `lancador_app_offline` checks the commands the launcher builds for the Gecko screen (off by default; when on, password file readable only by the user, `-viewonly`, no `-nopw`, websockify only for the page's origin) and `gecko/sobe.sh`; `atualizacao_git_api` checks that a real launcher leaves the screen's ports closed by default.
